# All-hands 2026-09-20, engineer seat: what can be built, in what order, and what breaks

Owner's question: "so what should we do?" This is the builder's answer only. Unit of cost is one engineer run (one OODA cycle, one draft PR). Small batch = 3 runs, big = a cycle. What exists today: cli/src/index.js, 114 lines, init and validate. Nothing mints, nothing runs.

## 2. The passport (proposal B), engineered minimum

- **Key material: a separate Ed25519 key per agent**, `.epito/keys/<agent>-passport.pem`, 0600, generated at first `epito passport`. Not the App PEM: GitHub owns that key's lifecycle (regenerable in the UI, which would void every past signature), it is the highest-value secret and should be loaded for one purpose only, and a Slack principal has no PEM at all (Slack hands out a bot token, not a key), so a platform-independent key is needed the moment there are two platforms. `node:crypto` signs Ed25519 natively, zero new dependencies.
- **Card**: `.well-known/agent-card.json`, a minimal A2A card (`name`, `description`, `url`, `version`) with an `epito` extension: `{ "v": 1, "agent", "manifest_sha256", "key": {JWK OKP Ed25519}, "identities": [ {"platform","id","uid","proof"} ], "issued_at", "sig" }`, `sig` an EdDSA JWS over the canonical JSON of everything else. The self-signature proves only possession of the key; the proofs do the binding.
- **GitHub proof, verifiable by anyone with read access to the repo**: the commit that writes the card is made through the Contents API with the agent's installation token, so its author is `<slug>[bot]` and GitHub signs it (`commit.verification.verified: true`). Verifier: `GET /repos/{o}/{r}/commits/{sha}` matches author login and uid, verified is true, and the blob at that sha hashes to the card. Second, cheaper pointer: the App's homepage `url` is set to the card URL in the manifest at mint, checkable at `GET /apps/{slug}`; mutual pointing (card names the slug, App names the card) defeats a stranger's App claiming the card. Honest unknown, verified in the spike: that Contents-API commits by an App carry the Verified badge; if not, the homepage pointer alone stands, which proves the App owner set it rather than the bot acting.
- **Slack proof**: Slack has no public surface, so this is workspace-scoped and stays that way. The bot posts one message carrying a JWS of its own `bot_id` and team id; a member verifies with `conversations.history` plus `users.info`. The card records `{"type":"slack-message","team","channel","ts"}`. The app manifest's description carries the card URL for humans.
- **Serving, local-first, no server of ours**: the agent's own repo. Card URL v0 is `https://raw.githubusercontent.com/<o>/<r>/<branch>/.well-known/agent-card.json`; when the user enables Pages the same file appears at `https://<o>.github.io/<r>/.well-known/agent-card.json`, the proper A2A path. epitod's port is never a proof surface (unreachable by a third party by design).
- **Cost**: `epito passport` (generate key, write card, commit as bot) 1 run; `epito passport verify <url>` (the three GETs above, green line or the exact failing check) 1 run; the Slack arm 1 run on top of the Slack provider.
- **Visible within cycle 2: yes for the mechanism on GitHub** (a third party runs `epito passport verify` and gets a green line, 2 runs). **No for the two-platform proof**, which is the actual outdo claim: it needs the Slack principal, so it lands at the end of cycle 2 only if Slack's mint is done by week 1, otherwise cycle 3. Say "one platform, mechanism proven" in cycle 2 and do not say more.

## 3. The network-path problem (market §8.2b)

Runtime v0 already answers it for us: an Actions runner has no `.epito/`, so the agent's key must reach the container as a secret and the 1h token is minted there. The key travels, not the token request. That is the same trust shape for any hosted runtime.

| Option | Tradeoff |
|---|---|
| Relay through the control plane early (hosted `mint` now) | A Vercel function, KMS, and Postgres a full cycle early; the PEM leaves the user's machine into our custody; first bill and first breach surface before a paying user; and we become load-bearing for the user's own agent (ADR-6). |
| User-run tunnel (`cloudflared tunnel`, `tailscale funnel`) to an epitod token port | Zero infra for us, but epitod is cycle 3, the laptop must be awake at cron time, and a token-minting port on the internet needs its own auth. A demo, not a product. |
| Pre-minted tokens injected at deploy | Dead on arrival: installation tokens live 1h, a daily cron holds an expired token. Slack bot tokens do not expire, which just means this is the stored-key pattern under another name. |
| Defer hosted targets to phase 3 | Cleanest, and §8.4 already says the LangSmith-hosted buyer is the one that is not ours. Loses only the recipe. |
| **Carry the agent's own key, mint in-container** (recommended) | `epito token` runs from `EPITO_APP_ID` + `EPITO_APP_KEY` env with no `.epito/`; `langchain-epito` reads the same env; LangSmith, Modal, anything with a secrets field gets the path for free. Their vault holds the agent's key, not the owner's: scoped by the manifest, revocable by `epito revoke`. Costs: rotation is a redeploy, and the audit line is written where the token is minted, so local `audit.jsonl` is blind to hosted runs until an audit sink exists (the OTLP export from §8.2a, or phase 3). One run, inside cycle 2's runtime work. |

Recommendation: env-only `epito token` in cycle 2, no relay before phase 3, tunnel documented as a recipe only when epitod exists.

## 4. What I would cut or refuse, and the cycle-1 risk

- **Refuse the toolchain migration inside cycle 1.** TypeScript strict, pnpm workspaces, tsc project references, biome, changesets, and a 2x2 CI matrix for 114 lines eats scope 2a's three runs whole. Do: `packages/core` as plain ESM JS in the one existing package, vitest, one CI job on Node 22. TS conversion is its own card after the cycle, still under the byte-identical test.
- **Drop `jose`.** `node:crypto` signs RS256 and Ed25519; a ten-minute JWT is base64url of two objects and one `sign` call. Fallback to jose only if the hand-rolled JWT bites in the spike.
- **Decide App-per-agent now, do not spike the choice.** A shared App gives every agent one badge, which kills attribution and the passport before either exists. The spike proves the manifest flow, not the route.
- **Cut** the `epito audit` read-back (`tail .epito/audit.jsonl` is the command), JWKS endpoints and key rotation from the passport, and any build on LangSmith custom-auth or Connections (watch, per §8.4).
- **Biggest risk to cycle 1:** two human clicks (Create, Install) sit inside `epito deploy`, so CI can never exercise the mint; every provider PR needs a hand-run against a real account, and with CLAUDE_CODE_OAUTH_TOKEN still missing the seat has no scheduled runs at all. Mitigation: MockAgent fixtures for `/app-manifests/{code}/conversions` and `/app/installations` carry CI; the owner or chair runs `epito deploy` in a throwaway repo once per provider PR and pastes the transcript. If no run convenes by 09-26, the PM's bet-swap clause fires.

## 5. Three recommendations, one by one

1. Decide App-per-agent today and skip the route debate: the spike proves the manifest flow works, and a shared App would give every agent one badge, which kills the passport before it exists.
2. Solve the hosted-agent problem by carrying the agent's own key into the container (env-only `epito token`), the same way runtime v0 on Actions must already work, and build no token server before phase 3.
3. Give the passport its own Ed25519 key and ship the GitHub arm in cycle 2 as a two-run slice, calling it a two-platform proof only once the Slack principal exists.
