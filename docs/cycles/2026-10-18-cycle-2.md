## Dogfood finding, filed not fixed (2026-10-18, this run)

HQ's engineer, running epito's own resident runtime on the host
(`alexandra-systems/engineer`, board ask to `pm/epitome`), reported the
hand-patched copy still running there carries a fix this repository's
`main` does not: a guard against writing to a log file descriptor
after it has been closed, which took the host's whole daemon down one
night. Checked against `cli/src/lib/runner.js` this run: real and
unfixed on `main` — `write()` in both `cloneAgentRepo` and
`executeAgent` calls `writeSync(fd, ...)` guarded only by `fd !== null`,
and `fd` is never nulled after `closeSync(fd)` in `finish()`, so a late
async callback (a child's pipe `error` event, for one) can still call
`write()` against an already-closed descriptor and throw `EBADF`
unhandled. The same report's other two claims were checked and do not
hold: per-seat OTEL resource attributes are already on `main`
(`cli/src/lib/trace.js`'s `childTraceEnv`, wired at `runner.js:521`),
and the board run-report gap it also named is not new — it is this
ledger's own `docs/ideas.md` entry ("The run report the company board
has been waiting for…"), already proposed. Filed as a fresh
`docs/ideas.md` entry and handed to the engineer seat; not a scope of
this bet, since the bet is the publish path and this is a resident-
runtime reliability gap. Reply posted to the asking seat on the board
in first person, same reasoning.
