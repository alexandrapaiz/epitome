## Standing risk (opened 2026-10-18, corrected 2026-10-23 ~18:5xZ)

The npm publish token (`NPM_TOKEN`) dies **2026-10-24T19:26:26Z UTC**
— not midnight, and not just "tomorrow": the token's own record gives
the exact second, roughly 24.5 hours from this pass. Re-requesting one
costs the owner a Touch ID and is worth avoiding if tonight's work
clears the real blocker instead.

**Correction to this file's own last entry.** 18:3xZ this pass flagged
`cli/package.json`'s `"license": "UNLICENSED"` as tonight's one
missing word and raised it to the owner as urgent. That was wrong in
kind, not in fact: the engineer ran the actual `npm publish` at 18:50Z
(not the dry-run) and the registry refused it at the name check —
`403 Package name too similar to existing packages exit,pino` — which
npm raises before it ever validates the request body. A licence field
is in that body. So the licence question is real (docs/ideas.md,
2026-10-18, still `proposed`, still the owner's call — nothing here
reassigns it) but it was never actually tested tonight and is not what
is blocking the clock; escalating it as urgent was premature, and this
pass does not spend a second urgent slot correcting it.

**The real blocker, and the decision this pass makes.** Unscoped
`epito` is refused permanently — the filter does not clear with time
and a new token changes nothing (two edits from `exit` and from
`pino`). `epitome` is already published by someone else, which also
collapses `epito.me` and `epito-me` onto the same refusal. Accepted,
checked by probe without publishing anything: `epito-cli`,
`epitome-cli`, `epito-agents`, `epito-mint`, `@alexandrapaiz/epito`.
The engineer handed the call to this seat rather than filing it
owner-only a second time, and separately asked the owner the same
question, non-urgent, noting it "does not need a Touch ID." Per
standards/pm.md §22, a package name is not money, accounts, secrets,
or this seat's own authority, and the 48-hour silence default cannot
clear before a 24.5-hour clock anyway — so this seat decides rather
than let the scope sit un-owned: **`epito-cli`**. It needs no browser
action, keeps the binary name (`epito`) a stranger types unchanged,
and is already verified available. The owner can overrule it in one
word before the rename merges; nothing here forecloses that.

Posting the actual `npm publish` stays a secrets/account action this
charter does not execute (no `.github/workflows/` file automates it —
checked, none reference `npm` or `NPM_TOKEN`), so it still waits on the
chair or the owner holding the token from Infisical directly. What
changed this pass is that the one engineering-shaped blocker left —

## Dogfood finding, filed not fixed (2026-10-18, this run)

HQ's engineer, running epito's own resident runtime on the host
(`alexandra-systems/engineer`, board ask to `pm/epitome`), reported the
hand-patched copy still running there carries a fix this repository's
`main` does not: a guard against writing to a log file descriptor
after it has been closed, which took the host's whole daemon down one
night. Checked against `cli/src/lib/runner.js` this run: real and
unfixed on `main` — `write()` in both `cloneAgentRepo` and
`executeAgent` calls `writeSync(fd, ...)` guarded only by `fd !== null`,
and `fd` is never nulled after `closeSync(fd)` in `finish()`, so a late
async callback (a child's pipe `error` event, for one) can still call
`write()` against an already-closed descriptor and throw `EBADF`
unhandled. The same report's other two claims were checked and do not
hold: per-seat OTEL resource attributes are already on `main`
(`cli/src/lib/trace.js`'s `childTraceEnv`, wired at `runner.js:521`),
and the board run-report gap it also named is not new — it is this
ledger's own `docs/ideas.md` entry ("The run report the company board
has been waiting for…"), already proposed. Filed as a fresh
`docs/ideas.md` entry and handed to the engineer seat; not a scope of
this bet, since the bet is the publish path and this is a resident-
runtime reliability gap. Reply posted to the asking seat on the board
in first person, same reasoning.
