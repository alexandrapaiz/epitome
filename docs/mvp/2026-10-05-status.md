# MVP status, 2026-10-05 night

Written by the chair while the owner was away, under her instruction to
produce a first working version. What the MVP is, what was proven tonight,
what is blocked on her hand, and the exact commands.

## The MVP, in one sentence

One seat of the owner's, running on the server from a manifest, with its
own GitHub App, opening pull requests as itself, no personal token in the
chain, installable with one npm command.

## Proven tonight, on the server

The engineer's merge candidate (the twelve-PR chain, branch
`engineer/2026-10-05-the-merge-candidate`) was installed on the host as a
second copy at `/srv/asc/repos/epitome-next`, beside the live v0 runtime,
which kept running. On that box, as the `seats` user:

- `epito validate agents` passes for all five of epito's own seats and
  reports the engine at 127.0.0.1:7233 answering: nothing `epito run`
  would refuse.
- `epito run agents --dry-run` shows the four schedules it would register
  on Temporal (engineer twice daily, market Fridays, okr monthly, pm
  Mondays) and exo presence-only.
- `epito ps agents` reads the roster back from the engine: no schedules
  registered yet, which is correct for a dry run.
- `epito deploy pm agents --dry-run` prints the exact GitHub App it would
  create (`pm-alexandrapaiz`, contents and pull requests and issues,
  installed on alexandrapaiz/epitome) and that no principal exists yet.
- The unit suite passes on the server.
- The routes command shows every seat on the box's own Claude login.

Not proven tonight, and why:

- A real GitHub App was not created. Creating it starts a listener on the
  host for GitHub's one-click callback, and that step was refused as a
  production deploy without the owner present. The account has no GitHub
  Apps today, so there is nothing to collide with.
- The schedules were not registered on the live engine for the same
  reason: the live runtime is v0, and swapping it mid-run would have
  killed the PM runs the event bus had just started.
- npm publish needs the owner's npm login. The package is packed and
  verified.

## The event bus, measured

The bus works mechanically. Every addressed message tonight was delivered
through both doors: a repository dispatch to the seat's workflow
(status 204) and a message into the seat's window on the host (outcome
"started"). The host log shows the PM seats of all four companies starting
on those messages and opening pull requests.

The seats then declined to act on the chairs' messages. The HQ PM found
that the sections of the PM standard the messages cite are not on main
(they are on the console pull request). The epitome PM found that its
vendored copy of the standard still says seats never message each other.
So the bus delivers and the standard, as merged, tells the seats to
distrust it. Two merges fix that: the console pull request at HQ, and a
re-vendoring of the PM standard into the products.

Lesson from my own hand: the chair tool takes the recipient as two fields,
seat and company. My first three handoffs set neither and went to everyone.

4. Create the pm seat's App, from your laptop, ten minutes:

   ```bash
   ssh -i ~/.ssh/asc-host -L 7788:127.0.0.1:7788 ubuntu@129.80.83.195
   ```
   then on the host:
   ```bash
   cd /srv/asc/repos/epitome-next && sudo -u seats node cli/src/index.js deploy pm agents --port 7788 --no-open
   ```
   open http://127.0.0.1:7788/ in your browser, click Create GitHub App,
   install it on alexandrapaiz/epitome when GitHub offers, then run the
   same deploy command once more to record the installation, and
   `sudo -u seats node cli/src/index.js token pm` to see the mint.
5. Put the roster on the engine, on the host:
   ```bash
   cd /srv/asc/repos/epitome-next && sudo -u seats node cli/src/index.js run agents && sudo -u seats node cli/src/index.js worker agents
   ```
   The worker is what runs seats off the queue; the systemd unit for it
   is in deploy/ on the branch.
6. `npm publish` from cli/ on the branch, once logged in.

After 4 and 5, the first pull request opened by `pm[bot]` from the server
is the MVP, and the launch post the backlog names as dogfood step 3.
